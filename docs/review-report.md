## Security and clinical invariants checked

The review also checked existing tenant-scoped repositories, clinical permissions, public response isolation, input validators, encrypted webhook secrets, append-only consent/audit protection, retention, throttling and LiveKit metadata. Existing functional coverage still passes for cross-tenant read/cancel/audit denial, other-doctor attendance denial, unknown/untrusted host rejection, public props without account/permissions/flash, immutable accepted consent/version/hash, expired/wrong-clinic links and idempotent signed LiveKit callbacks. LiveKit metadata remains exactly `{role}`; video needs consent **and** explicit doctor admission.

Consent hash comparison now uses `timingSafeEqual` after fixed-length validation. Random link/session secrets are hashed and selected through scoped indexed database queries; this is not a JavaScript string equality loop over secret candidates. Incoming LiveKit signature/body verification remains delegated to its official receiver. The Clínica Fácil receiver must implement constant-time HMAC verification and durable replay deduplication; that receiver was not built here.

No new schema columns/tables were needed in open-telemed. Existing unique clinic/external-id constraints and the durable encrypted webhook outbox were reused; role setup was updated in the original pre-1.0 migration and shared synchronization code. No development database recreation or seed was needed. Existing service tokens do not automatically acquire new abilities and must be reissued deliberately.

The new `WEBHOOK_ALLOWED_ORIGINS` setting is documented in `.env.example`. Configure it before enabling deliveries; none is allowed by default. No actual infrastructure address or credential is included in these reports. The owner moved private test destinations into ignored `.env.test.local`; the subsequent full suite passed with that configuration.

## LiveKit termination limit

The [official token documentation](https://docs.livekit.io/frontends/reference/tokens-grants/) distinguishes Cloud token revocation from self-hosted behavior: participant removal/permission changes do not invalidate already issued self-hosted tokens, and refreshed tokens have a minimum ten-minute expiration. Therefore, the application's initial 60-second JWT lifetime does **not** bound every cached token's lifetime. [DeleteRoom](https://docs.livekit.io/reference/other/roomservice-api/) disconnects participants in that room; it is not proof of permanent access revocation.

`finish` persists the terminal state, prevents further application-issued tokens and requests room deletion. The lock now prevents application token issuance from recreating the room after that state change. Residual risks remain: a still-valid cached token, and failed room deletion (currently a sanitized warning without a durable close retry). Strict end-of-consultation access revocation requires a provider/deployment strategy and reliable cleanup. No real adversarial reconnect after termination was measured; the provider behavior above is documentation evidence, not a claim of an observed exploit in this environment.

## Integration decisions and owner questions

The implemented contract adds idempotent creation, scheduled-only update, explicit link reissue, scoped professional lookup, timestamped signed events and shared permission synchronization. [OpenAPI](openapi.yaml) descriptions are English; the machine contract and both integration documents agree on response envelopes, errors, retries, link expiry and the signing format. The timestamp-prefixed signature is a change from body-only signing and requires receiver coordination.

Read-only Clínica Fácil inspection covered its project instructions, agenda/attendance/team/assistant rules, WhatsApp sending/assistant rules, feature/tenancy/RBAC rules and corresponding implementation paths. Concrete conclusions: attendee can differ from customer; CRM fields are free text; rescheduling creates a new appointment; delivery must use the existing WhatsApp service/window/template rules; operational outcomes cannot become authored clinical notes. No files, tests, development server, migrations or seeders were changed/run there.

Questions left to the owner, with proposals in the integration document:

1. Approve one service identity per clinic, verified professional mapping, lifecycle/rotation and a future SSO design. Neither ticket login nor automatic API account provisioning was implemented.
2. Define reconciliation between agenda and telemed states, including failed compensation on rescheduling and in-progress calls. Preserve Quark/checkout and native booking ownership.
3. Decide recipient versus patient/representative, approved messaging templates, feature entitlements and role capabilities.
4. Decide historical clinician snapshots, record export/authorship, retention responsibilities and deployment/legal validation against [the supplied clinical requirements](brazil-telemedicine-rules.md). This code review is not certification of an SRES or regulatory compliance.
5. Choose strict video revocation, durable room-close retries and webhook/reconciliation operations. Keep approved destinations and secrets operator-controlled.
