# Headless integration report

Date: 2026-11-26. Executed [the headless specification](spec-headless-integration.md) in open-telemed, without commits. Clínica Fácil remained read-only: no edits, tests, dev server, migration or seed there. Its future UI/BFF, signing backend, webhook receiver and record importer are specified in [the updated integration document](clinicafacil-integration.md), not claimed as deployed.

## Decisions 1–5

| Owner decision                                             | Recommendation and implementation                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Native Clínica Fácil experience, without a second login | Clínica Fácil renders doctor and patient flows through its own BFF. Implemented nine engine endpoints, operator-pinned connection/key/subject mappings, one-use action-scoped doctor assertions and opaque patient sessions. Configured patient links point to its frontend; `doctor_url` is null. Legacy public exchange and panel attendance are blocked for headless clinics. LiveKit React components belong inside Clínica Fácil's own layout. |
| 2. Agenda ↔ teleconsultation reconciliation                | Separate local and remote states with transactional outbox/inbox, idempotent creation and monotonic revision. Added revision to records/events, preserved historical professional identity in events, and made `room_finished` an operational interruption rather than invented completion. The detailed mapping preserves native status/queue/checkout rules and treats remarcação as a new appointment.                                           |
| 3. Recipient and template                                  | Confirm the patient or authorized representative explicitly; never equate attendee with customer/lead. Use the existing WhatsApp service, stable delivery-intent id and a neutral approved utility template outside the window. No unverified automatic recipient or assistant-generated secret URL. Template/button behavior must be qualified in Clínica Fácil.                                                                                   |
| 4. Identity snapshot and attributed export                 | Implemented immutable doctor name/CRM/UF/RQE and identifiers at admission, or an explicit no-show decision. Versioned export separates doctor, patient and system authors, and separates clinician identity from the service carrying the assertion. Existing uncaptured history remains null; no retrospective authorship was invented.                                                                                                            |
| 5. Video revocation                                        | Recommend LiveKit Cloud with an explicit revocation cutoff, durable recovery and verified deployment clocks. Implemented both-identity removal before deletion, transactional closure outbox, retry command and handling of terminal late joins. GET exposes closure progress separately from clinical outcome; self-hosted closure explicitly reports `tokens_revoked:false`.                                                                      |

Rejected alternatives: iframe/custom-host engine UI duplicates sessions/UI; shared login or broad integrator impersonation weakens scope; synchronous dual writes cannot atomically update both systems; blind state copying bypasses agenda guards; automatic delivery to the current lead risks reaching the wrong person; room deletion/client disconnect alone cannot prove token revocation. The selected alternatives and compensation rules are detailed in the integration document.

## Implemented files and behavior

- `app/modules/headless/`: modular routes/controllers, assertion and consent-evidence validators, connection/nonce repository, access and operator configuration services. Four doctor actions (`state`, `admit`, `video-token`, `end`) and five patient actions (`session`, `state`, `consent`, `video-token`, `decline`) use server-side credentials, scoped permissions and no-store responses.
- `commands/configure_headless.ts`, `map_headless_doctor.ts`, `prune_headless_assertions.ts`: configure a single-clinic service identity, pin a public key/issuer/patient URL, map a verified doctor, and prune expired replay markers. Changing issuer with existing mappings is rejected; connection locking serializes configuration with mapping changes. Signing private keys are never stored in the engine.
- `consultations/services/patient_service.ts`, `consultation_service.ts`, `consultation_access_service.ts`: existing consent/admission/ownership transactions are reused. Patient BFF sessions remain consultation- and tenant-bound; revocation is rechecked under lock. Headless clinician authorization does not create an engine login or grant generic integrator attendance.
- `consultations/services/clinical_record_service.ts`, `consultations/models/consultation.ts`, original `create_consultations_table` migration: snapshot, attribution, revision, schema-versioned export and PostgreSQL guards against snapshot/author replacement or removal. Snapshot capture locks both professional and user sources. Completion/referral requires in-progress; no-show may capture identity at the explicit decision.
- `consultations/services/consultation_event_service.ts`: event revision advances under the consultation transaction; events use frozen CRM/UF after capture and expose a compact author summary. GET provides the full record. Provider callbacks cannot invent a medical outcome.
- `shared/services/video_service.ts`, `consultations/services/video_closure_service.ts`, `livekit_webhook_service.ts`, `commands/close_videos.ts`: durable terminal closure, provider-error sanitization, concurrent-worker serialization and retry of late terminal joins. Cloud calls include explicit cutoff and both deterministic participant identities; self-hosted mode makes no cached-token revocation claim.
- New migrations create genuinely new objects only: `headless_connections`, `headless_identities`, `headless_nonces` and `video_closures`. Existing consultation columns and permission defaults were changed in their original pre-1.0 migrations. Existing audit/consent trigger functions now use `CREATE OR REPLACE FUNCTION`, allowing `migration:fresh` when functions survived table removal.
- `docs/openapi.yaml`: all headless endpoints, security headers/claims, patient session transport, consent evidence, snapshot/authorship, revision, interruption and `video_closure`. Added the English specification; updated both integration documents. No README or screenshot files were edited.

## Short threat model

| Threat                                            | Enforced boundary and remaining trust                                                                                                                                                                                               |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stolen service token used to attend               | Doctor actions also require a valid pinned RS256 assertion for the assigned mapped clinician; service identity cannot substitute for clinician identity.                                                                            |
| Manager, root, other doctor or other clinic       | Exact connection/service/tenant checks, active clinician membership, doctor role and attendance grant, assigned professional and signed consultation/action are all required. Root is refused.                                      |
| Forged, expired or replayed assertion             | Pinned key/issuer/audience/algorithm; positive lifetime ≤60 seconds; bounded issuance time; required UUID nonce consumed atomically. No caller-supplied key URLs. The concurrency regression admits exactly one reuse.              |
| Changing operation or outcome                     | Action and consultation are signed; end outcome comes from the signed assertion. No arbitrary target user is accepted by an attendance endpoint.                                                                                    |
| Stolen patient credential or cross-tenant swap    | Per-consultation opaque session, tenant binding, expiry, explicit consent and admission, revocation recheck. The BFF must protect its cookie/session store and enforce CSRF/public throttling.                                      |
| Clinical authorship rewritten after profile edits | Immutable snapshot and finalized attribution, application checks plus PostgreSQL triggers. Patient refusal/admin cancellation never become doctor-authored conclusions.                                                             |
| Trusted Clínica Fácil signer compromised          | It can impersonate its mapped clinicians. This federation boundary requires protected private keys, current authenticated-user checks and auditing on that side; engine checks cannot prove which person used a compromised signer. |
| Terminal video request or provider failure        | Existing issuance lock prevents new application tokens after termination; closure work persists atomically and stays pending on failure. Provider-mode claims and actual Cloud enforcement still require deployment qualification.  |

The [LiveKit token contract](https://docs.livekit.io/frontends/reference/tokens-grants/) distinguishes Cloud revocation from self-hosted behavior. The chosen implementation uses a cutoff one second ahead to include same-second tokens; synchronized clocks and real Cloud reconnection tests remain required. Tests validate SDK calls and recovery with controlled provider faults, not a deployed Cloud revocation guarantee.

## Authorship and Clínica Fácil responsibilities

The export is an attributed encounter summary, not a clinical narrative, prescription or digital medical signature. `professional_snapshot` freezes identity; `outcome_author` identifies who decided the outcome and when. Delegated audit includes the service/connection separately. GET's `video_closure` distinguishes pending/completed and `tokens_revoked`; clinical termination can precede physical media closure during provider failure.

The read-only review confirmed that Clínica Fácil's attendee can differ from customer, registration fields are free text, rescheduling creates another appointment, and its notes are immutable and restricted to the current attending author with root denied. Therefore its implementation should import encrypted encounter artifacts under verified author provenance, not make a service user write a doctor's note. Explicit adoption/reference by an authorized doctor remains separate.

Its remaining work is concrete: native doctor/patient UI and BFF; signing service and verified mappings; feature/team capabilities; booking/status/queue intents; inbox/outbox/reconciliation; verified recipient/template delivery; encrypted imported encounter storage and access rules. Live Quark mirror automation is excluded from the initial recommendation. No paid/provider account, production service or new clinical-identity federation was provisioned against real Clínica Fácil data.

## Development recovery and gate

The owner authorized recreation of **only** the open-telemed development database using the existing full/data dumps as recovery. All preserved data was restored transactionally and **13 consultations were verified**; no seed was executed. The PostgreSQL client's unsupported `transaction_timeout` session directive was removed from the restore stream for compatibility with the server, without changing data. Permission synchronization then succeeded. No other database or container was changed. Historical rows were not backfilled with invented snapshots.

All gates ran with Node **24.21.0**, pnpm, bounded systemd memory scopes and two Vitest workers. Private test destinations remained in ignored `.env.test.local`; no real infrastructure host/IP or machine path is included in this delivery.

The total adds **26 tests** to the prior 253: ten headless boundary/concurrency cases, nine clinical-record cases and seven closure/recovery cases. Existing room-finished expectations were corrected to distinguish operational interruption from medical conclusion. API assertions validate successful headless responses against OpenAPI, including authored export and closure status. The existing browser suite still exercises real LiveKit with synthetic media; Clínica Fácil browser flows were not run.

RED evidence preceded the snapshot and headless implementations. Focused integration passed **53/53** before the complete gate. The initial complete run found a missing original-migration permission entry, which was corrected; subsequent complete runs passed. Independent review found and led to fixes for mutable webhook identity, stale state serialization, and issuer/mapping serialization. The final issuer-lock race was established by code analysis, not claimed as a reproduced concurrency test.

Nonblocking warnings: unset package-registry token placeholder, large video bundle, and media teardown data-channel messages. No warning was suppressed. Local logs and recovery dumps are retained outside the repository. The development server is restored on port 3333; its login page responds HTTP 200.

Limits: no real WhatsApp/template approval, no Clínica Fácil runtime implementation, no Cloud provider reconnection qualification, no physical device/TURN matrix, no load benchmark, and no regulatory or SRES certification. These are explicit rollout work, not unimplemented engine authorization paths.
